How it works — and why every answer is safe

The point of this system is trust. A language model can hallucinate a query or be talked into reaching for data it shouldn't. Here, the model only ever proposes SQL — a security guard decides whether it runs.

1
You ask in plain English.
2
The model writes SQL against a fixed, published schema (see “What's inside”).
3
The guard validates it before anything runs: SELECT-only, allow-listed tables, an automatic row cap, no system/catalog access, no file-reading. A denied query is refused at the boundary — you see the reason.
4
The safe query runs and you get rows back, plus the exact SQL the guard ran and what the call cost.

What it can never do

Write or change data (read-only), touch a table outside the allow-list, read the file system, or return more than the row cap — no matter what the model is convinced to write. Every decision (allow / deny) is auditable.

Try it: on the Ask tab, ask “list every table in the database” — a reasonable-looking request the guard refuses, because it reaches for the catalog.
